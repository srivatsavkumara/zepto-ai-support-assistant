# Zepto Policy Support Assistant — RAG Module

A small, fully offline-gradable RAG service over Zepto's own delivery, returns,
membership, tracking, cancellation, gift card, and support-hours policies.

## A note on file layout (please read first)



| Notebook | Generates | Purpose |
|---|---|---|
| `00_setup.ipynb` | `docs/doc_01..08.txt`, `requirements.txt`, `Dockerfile` | materializes everything that isn't pipeline logic but must exist as a real file |
| `01_ingest.ipynb` | `ingest.py` | load docs, chunk, embed, ChromaDB build + retrieval |
| `02_prompt_template.ipynb` | `prompt_template.py` | role–context–task–format–length prompt (optional-extension use) |
| `03_graph.ipynb` | `schemas.py`, `graph.py` | Pydantic schema + LangGraph `StateGraph` (3 nodes, conditional edge, `MOCK_LLM` gating) |
| `04_app.ipynb` | `main.py` | FastAPI app, `POST /ask` |
| `05_demo.ipynb` | *(none — a runner)* | starts `uvicorn`, fires the 2 required example calls, prints raw JSON |

The `Dockerfile` does this same execution automatically at build time via
`jupyter nbconvert --execute`, so the image is self-contained.

## Quick start (local, graded baseline — MOCK_LLM left at default)

```bash
cd support_assistant
jupyter nbconvert --to notebook --execute --inplace 00_setup.ipynb   # writes docs/, requirements.txt, Dockerfile
pip install -r requirements.txt
jupyter nbconvert --to notebook --execute --inplace 01_ingest.ipynb
jupyter nbconvert --to notebook --execute --inplace 02_prompt_template.ipynb
jupyter nbconvert --to notebook --execute --inplace 03_graph.ipynb
jupyter nbconvert --to notebook --execute --inplace 04_app.ipynb
uvicorn main:app --host 0.0.0.0 --port 7860
```

Or open and run `01_ingest.ipynb` → `04_app.ipynb` top-to-bottom in Jupyter, then
run `05_demo.ipynb` to spin the server up, fire both example calls, and print
their JSON automatically.

## Docker (required, graded baseline)

```bash
docker build -t zepto-assistant .
docker run -p 7860:7860 zepto-assistant
curl -X POST http://localhost:7860/ask -H "Content-Type: application/json" \
     -d '{"query": "How long do I have to return a spoiled item?"}'
```

This is the required, graded baseline — no push to a registry or Space is needed.

## Architecture: ingestion → embedding → retrieval → generation

**1. Ingestion** — `ingest.load_documents()` (in `ingest.py`, generated by
`01_ingest.ipynb`) reads the 8 policy files from `docs/doc_01.txt` … `doc_08.txt`
off disk. `ingest.chunk_document()` produces one chunk per document (each source
document is a single short, topically self-contained policy paragraph, so
per-document chunking is the simplest correct scheme for this corpus; it falls
back to fixed-size splitting if a document ever exceeds 400 characters).

**2. Embedding** — `ingest.build_or_load_collection()` embeds every chunk locally
with `sentence-transformers/all-MiniLM-L6-v2` (no API key, no network call beyond
the one-time model download) and upserts the vectors into a persistent ChromaDB
collection named `zepto_policies` (cosine-similarity index), stored on disk under
`./chroma_db`.

**3. Retrieval** — happens inside the `retrieve_and_answer` LangGraph node
(`graph.py`, generated by `03_graph.ipynb`), which calls `ingest.retrieve_top_k()`
to embed the incoming query and pull the top-3 most similar chunks from the
`zepto_policies` collection. This retrieval step runs for real in **both**
`MOCK_LLM` states, since it needs no API key or network call.

**4. Generation** — also inside `retrieve_and_answer` (for `policy_question`
queries) and inside the separate `direct_answer` node (for `general_question`
queries, no retrieval). Both nodes branch on `MOCK_LLM`:
   - **Mock (default, graded):** `retrieve_and_answer` builds a canned
     `f"Based on the retrieved context: {top_chunk_snippet}"` string from the
     top retrieved chunk; `direct_answer` returns a fixed canned string. Neither
     makes any LLM or network call. The `AskResponse` (`answer`, `sources`,
     `confidence`) is populated deterministically by code in both nodes.
   - **Optional `MOCK_LLM=0` extension:** `retrieve_and_answer` sends the
     retrieved chunks through the structured prompt template
     (`prompt_template.build_messages()`, from `02_prompt_template.ipynb`) to a
     real LLM (Groq free tier by default); `direct_answer` prompts the LLM
     directly with no retrieval context. Both validate the raw LLM output
     against the `AskResponse` Pydantic schema and retry up to 2 additional
     times with a corrective instruction on validation failure
     (`graph._call_llm_for_json()`), returning a clearly marked `[ERROR] ...`
     response if all retries are exhausted.

**Routing** — `classify_intent` (also `MOCK_LLM`-gated: keyword heuristic vs. LLM
call) decides `policy_question` vs `general_question`; a LangGraph conditional
edge (`route_by_intent`, which does **not** depend on `MOCK_LLM`) sends the state
to `retrieve_and_answer` or `direct_answer` accordingly. All of this is wired in
`graph.build_graph()` as a `StateGraph(GraphState)` with a `TypedDict` state.

```
query
  │
  ▼
[classify_intent]  (MOCK_LLM-gated: keyword heuristic | LLM call)
  │
  ├── policy_question ──▶ [retrieve_and_answer]
  │                          │ 1. ingest.retrieve_top_k()  (always real: ChromaDB + MiniLM)
  │                          │ 2. MOCK_LLM-gated answer:
  │                          │      mock → canned "Based on the retrieved context: ..." template
  │                          │      real → prompt_template.build_messages() → LLM → schema-validated
  │                          ▼
  │                       AskResponse(answer, sources, confidence)
  │
  └── general_question ──▶ [direct_answer]
                             │ MOCK_LLM-gated answer:
                             │   mock → fixed canned string
                             │   real → LLM, no retrieval context
                             ▼
                          AskResponse(answer, sources=[], confidence)
```
